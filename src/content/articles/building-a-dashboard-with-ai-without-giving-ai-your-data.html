A Google Sheet can be used to store a program's enrollment, attendance, and outcome data. As the sheet grows to hundreds of rows, specific answers can become hard to find, such as how many learners are active at each site or which learners have stopped attending.

A dashboard built on that sheet can show those answers directly. Instead of scrolling through rows, staff can see totals by site, filter the list to one site or class, and click a learner's email address to copy it. With that information in one place, staff can follow up with learners sooner.

Building a dashboard once required someone who could write code. AI tools now make it possible for staff who are not developers to build one themselves.

Learner records stay in a Google Sheet

When a dashboard displays learner records, privacy is often the first consideration. Two questions usually come up: who else will be able to see the records, and will the AI tool used to build it have access to them?

Both questions have the same answer. The records stay in the Google Sheet where they are already stored. A dashboard built with Google Apps Script reads them from that sheet without copying or moving them, and the sheet keeps the sharing settings you have already chosen. Anyone who could not open the sheet before the dashboard existed still cannot open it. The AI writes the instructions for the dashboard without ever accessing the records.

Protecting learner information therefore works the same way it does for any Google Sheet: only the people you choose can open the sheet or the dashboard.

You choose who can open the dashboard when you publish it. Google asks who should have access, with choices such as only you, anyone in your organization, or anyone with a Google account. If you choose your organization, only people signed in with your organization's accounts can open it, and anyone else is denied access. Staff who use the dashboard do not need access to the sheet itself.

The dashboard can also show each person only the records they work with, such as the learners at their site. It does this by checking the work account each person signed in with. You could also give each staff member a separate link that opens only the records for their site. Anyone who receives a copy of that link, however, can open the same records. Separate links work well for information that is not sensitive, such as an interactive class catalog with a link for each site that learners can filter by program area. For learner records, the work account sign-in is the safer choice.

Two other options can make access easier to manage. The first is a password. You can ask the AI to add a sign-in screen to the dashboard, then give the password to the staff who need it. Anyone who learns the password can open the dashboard, though, so this option suits summary information better than individual learner records.

The second option is a staff access list. You can ask the AI to have the dashboard read a "Staff access" tab in the sheet, or to build an admin page inside the dashboard, where you list each staff member's email and the site they work with. Giving a new staff member access, or removing access when someone leaves, then means editing one row, or using an "Add staff member" button on the admin page without opening the sheet at all. Program leaders can manage access themselves, without changing any code.

AI writes the code without accessing learner records

The dashboard is built with Apps Script, Google's built-in tool for adding features to Workspace files. If you've used a Sheets or Forms add-on, such as autoCrat or Yet Another Mail Merge, you've used a tool built with it. For a dashboard, Apps Script reads the rows in your sheet and displays them as a web page with charts, totals, and lists. It can also write information back to the sheet. A staff member could log a follow-up call in a short form on the dashboard, and the call would appear as a new row in the sheet. Apps Script can also send emails, such as a weekly message to each site coordinator listing the learners at their site who have missed two weeks of class. It can create custom exports or open a pop-up window with one learner's details, so a dashboard can grow into a small app built around how your program works.

AI can write the Apps Script code, and it needs only two things to do it. The first is the structure of your sheet: the tab names and column headers, such as "Site" or "Hours Attended." The second is a description of what the dashboard should show and do, such as "Add a button that creates a print-ready sign-in sheet for each class." The AI does not need to see or access any learner's record.

You then paste the code the AI writes into Apps Script in your own Google account.

The simplest way to open Apps Script is from the sheet's Extensions menu. Opening it there connects the script to that sheet, so you don't have to look anything up or paste anything into the code. Tell the AI you are working this way so the code it writes matches. When someone opens the dashboard, the code reads the sheet inside Google Drive. Learner records never pass through the AI.

A dashboard can also combine information from more than one sheet. For example, a program might keep enrollment in one sheet, instructors might record attendance in another, and a Google Form might collect learner survey responses in a third. One dashboard can show all three side by side, even when different staff maintain each sheet, and one button can export the combined information for a funder or state report.

Apps Script also works with Google Forms, Docs, Slides, and Calendar, so a dashboard can connect to the other tools a program already uses. A registration submitted through a Google Form could appear on the dashboard and add the learner to an orientation session on the program's calendar. A button could fill in a welcome letter in Docs with each learner's class and start date, or create a certificate in Slides for each learner who completes a course.

To use another sheet, the dashboard needs that sheet's ID, a string of letters and numbers in the sheet's web address. You can paste the ID into the code yourself or give it to the AI so the code is ready to use. Like a link, the ID points to the sheet but opens nothing without the owner's permission. The AI cannot open the sheet with it, and the sheet's sharing settings stay the same.

The main risk is sharing learner records with AI by accident

The risk to be mindful of is a staff member sharing learner records with an AI tool while asking it for help. An AI tool can access learner records only when someone shares them, such as by pasting rows into a chat, uploading a screenshot of the sheet, or connecting the tool to Google Drive. This usually happens without anyone intending it, while someone is trying to fix a problem quickly. The example below shows one way to ask for help without including any records.

An enterprise or education license can add protection. These organization-wide agreements generally keep your data out of model training and let administrators control how staff use the tool. If your agency has one, connecting the tool to your files may be permitted under its terms. Your IT department or technology director should be able to tell you which tools are covered.

The permission screen applies only to your own account

The first time the dashboard runs, Google asks you to authorize it. The screen names the project, which appears as "Untitled project" until someone renames it. It also warns that Google hasn't verified the app, because the script has not gone through Google's review for public apps. Finally, it lists what the script can do, such as see and edit your spreadsheets. That list can look alarming, but the access stays within your own account. The script runs as you, on files you can already open, and it gives no one else access, including the AI.

Approving the script still asks you to trust code you did not write yourself, so it is reasonable to be careful. You can rename the project so you recognize it, test the dashboard on sample data first, or ask your IT staff to look over the code.

Sample data lets you build skills before using real records

Building a dashboard on learner records can seem intimidating, and it makes sense to be careful with learner information. A good way to begin is to practice building dashboards before any real records are involved.

Start with sample data. For example, a program director might ask the AI: "Create a spreadsheet with columns for Learner ID, Site, Start Date, Hours Attended, and Last Attended, filled with 40 sample learners across three sites." Next: "Write Apps Script for a dashboard that shows active learners by site and lists anyone who has not attended in 14 days." Then: "Add a chart of weekly attendance hours for each site, and let me copy a learner's email address by clicking it." Building and adjusting a dashboard this way shows how the process works, with no learner information involved.

Many useful dashboards also involve no sensitive information at all. A program could track staff professional development hours, class schedules and room use, or the number of referrals from community partners each month. These make good first projects for staff who want practice before working with learner records.

When you are ready to use real records, connect the dashboard to the real sheet and share it with one site coordinator for a few weeks. Their feedback can show what to change before the rest of the staff use it. At no point does the AI need access to a real learner's record.

Store the sheet and the dashboard in a shared drive your program owns. If the person who built the dashboard leaves the organization, another staff member can update and republish it.
